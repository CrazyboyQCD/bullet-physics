# Bullet parity comparison ledger

> Frame-by-frame numerical comparison between Bullet (C++, `refs/bullet3`) and
> this crate. Report rows are generated by `tools/compare.py`; classification
> columns are filled in manually against `docs/bullet-deviations.md`.
> Harness design and run instructions: `docs/parity-harness.md`.
> Created 2026-08-14 (first scene: `falling_box`, f32 pair).

## Run protocol

One command runs the whole pipeline (library self-check, recorder build,
both recordings, diff, ledger update):

```
python tools/parity.py --update-ledger   # per scene; exit 0 = within tolerance
python tools/check.py --parity           # full regression + parity snapshot
```

Under the hood:

- Bullet: `refs/bullet3` built with CMake 3.31 + MSVC (VS2022), Release,
  static `LinearMath`/`BulletCollision`/`BulletDynamics` libs only. Recorder:
  `tools/bullet_record.cpp` (`tools/build_recorder.py`), solver mode =
  defaults with `SOLVER_RANDMIZE_ORDER` cleared, `dt = 1/60`, 10 iterations.
- Rust: `cargo run -p bullet --example record_scenes` (f32 default). Both
  recorders read scene tables generated from `tools/scenes.json` (single
  source of truth, see `tools/generate_scenes.py`).
- Output: `target/<scene>_<body>_bullet.csv`, `target/<scene>_<body>_rust.csv`
  (one line per frame: `t px py pz qx qy qz qw`) plus
  `target/<scene>_report.md` (markdown section for this ledger).
- The numeric report section below is regenerated by `parity.py`
  (`--update-ledger`); the classification section stays manual.

### Actions taken

- **Fixed** (implementation problem, found by this scene): friction and
  restitution combination were `√(f₁·f₂)` / `max(r₁,r₂)` but Bullet uses the
  products `f₁·f₂` / `r₁·r₂` (`btManifoldResult::calculateCombinedFriction` /
  `calculateCombinedRestitution`). Corrected in
  `crates/bullet-dynamics/src/solver/sequential_impulse.rs`; orientation dev
  dropped 0.0196 rad → 0.000135 rad and resting drift ~3x smaller. All 119
  tests still pass. `docs/bullet-deviations.md` §4 updated.
- No unbounded drift, directional bias, energy injection, or divergence
  observed: the scene passes the design tolerances outside the 10-frame
  impact window.

### Difference classification

Analysis: Bullet's stack is essentially at rest from the first frame (total
sink 0.7 mm); ours compresses gradually over ~60 frames to a stable rest
2.3-3.5 mm lower per interface (13.8 mm at the top box), then holds — no
collapse, no unbounded drift, so manifold reduction and stack stability match.
The resting offset is the documented slop + predicted-pose trade-off scaled by
stack depth: penetrations below the (slop − g·dt²) no-correction zone are never
corrected, so each interface rests ~2.3 mm deep while Bullet's
`m_linearSlop = 0` corrects any penetration. Diagnostic: with `SLOP = 0` the
top box rests within 0.4 mm of Bullet, confirming the slop zone (not a solver
convergence bug) is the cause. The small transient at frames 56-66 is the
one-step contact-detection phase offset on the initial settle.

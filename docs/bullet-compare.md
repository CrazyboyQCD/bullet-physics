# Bullet parity comparison ledger

> Frame-by-frame numerical comparison between Bullet (C++, `refs/bullet3`) and
> this crate. Report rows are generated by `tools/compare.py`; classification
> columns are filled in manually against `docs/bullet-deviations.md`.
> Harness design and run instructions: `docs/parity-harness.md`.
> Created 2026-08-14 (first scene: `falling_box`, f32 pair).
>
> 2026-10-19: all scenes re-recorded on the integration-quality branch
> (exponential-map rigid pose integration + the default-on implicit
> gyroscopic impulse). Non-rotating scenes stay digit-identical; rotating
> scenes shift within their recorded classes; `mesh_parts` picks up a
> Bullet-side knife-edge flip (its recorder binary drifted past a deep-
> recovery vs tunnel boundary — full root-cause in its sections).

## Run protocol

One command runs the whole pipeline (library self-check, recorder build,
both recordings, diff, ledger update):

```
python tools/parity.py --update-ledger   # per scene; exit 0 = within tolerance
python tools/check.py --parity           # full regression + parity snapshot
```

Under the hood:

- Bullet: `refs/bullet3` built with CMake 3.31 + MSVC (VS2022), Release,
  static `LinearMath`/`BulletCollision`/`BulletDynamics` libs only. Recorder:
  `tools/bullet_record.cpp` (`tools/build_recorder.py`), solver mode =
  defaults with `SOLVER_RANDMIZE_ORDER` cleared, `dt = 1/60`, 10 iterations.
- Rust: `cargo run -p bullet-physics --example record_scenes` (f32 default). Both
  recorders read scene tables generated from `tools/scenes.json` (single
  source of truth, see `tools/generate_scenes.py`).
- Output: `target/<scene>_<body>_bullet.csv`, `target/<scene>_<body>_rust.csv`
  (one line per frame: `t px py pz qx qy qz qw`) plus
  `target/<scene>_report.md` (markdown section for this ledger).
- The numeric report section below is regenerated by `parity.py`
  (`--update-ledger`); the classification section stays manual.

  tests still pass. `docs/bullet-deviations.md` §4 updated.

  impact window.

### Difference classification

Analysis: the sphere passes the falling_box profile — free fall bit-identical,
one-step phase offset on impact (10 frames, predicted-pose detection), then
rest within the slop tolerance (Rust y = 0.5012 vs Bullet 0.5000). The box
rests ~17 mm off horizontally: on a 1 m-cell mesh the box's bottom face always

Rust ~2-4 mm). No collapse, no unbounded drift.

**2026-08-26 persistent-manifold round**: the sphere no longer freezes
— the per-pair impulse inheritance removed the numerical damping that
used to stop it, and a sphere on the flat mesh keeps a slow creep
(physically correct: no rolling friction), so its orientation drifted
from Bullet's (0.017 rad max after ~3 s, exceedances from frame 177).
Positions stayed within the old envelope. See deviations §1
"persistent manifold cache".

**2026-08-27 sphere-triangle analytic fast path** (Bullet's
`SphereTriangleDetector` port): sphere contacts on the mesh no longer go
through GJK+EPA. Positions are bit-identical to the EPA path on the flat
ground (EPA already converges to the exact plane contact there), but the
orientation drift above is gone — the analytic normal/point remove the
last-ulp EPA noise that fed the creep divergence, and the sphere's
rolling now tracks Bullet's exactly (ang max 0.000000, exceedances drop
255→10 / f64 258→10: only the impact phase offset remains). The box rows
are unchanged (the fast path only covers spheres).

**Implementation problem found and fixed (this scene)**: contact positions for  
GJK+EPA pairs were the midpoint of the two shapes' *support* points; a mesh     
triangle's support along -normal lies far from the overlap, so mesh contacts    
had garbage positions and the solver's torque arms were wrong — on the
original ridge terrain the bodies neither tumbled nor rolled downhill like      
Bullet's. Fixed to Bullet's witness-on-B (`support(A, n) - n·depth`, commit

correct downhill rolling).

comparison within 1e-2 is not meaningful for rolling dynamics. The scene was    
reduced to the flat ground for the stable regime; the ridge findings are        
recorded here.

sphere-on-mesh contact now accumulates manifold points across frames like

### Implementation problem found and fixed

**Rigid-side double-counted relative velocity in mixed contact rows.** The
multibody contact iteration read the rigid side's *real* velocity (gravity +
assembly velocity included) while the rhs already carries `-rel_vel` — the
assembly-time relative velocity entered the impulse twice, inflating the
rb→mb impulse ~2.4x (first-hit Δv 8.2 m/s vs Bullet's 3.4 m/s). Static-rigid
partners never read their side and mb↔mb pairs use the zero-based delta pool,
so the phase C unit tests (resting, pushing, wake-up) stayed green while any
fast rigid→multibody hit was wrong. Fixed by snapshotting each rigid side's
row projection at assembly (`SideData::Rigid::initial_proj`) and reading the
impulse delta (current projection − snapshot) in `solve_row`, matching
Bullet's delta-velocity pools (`m_deltaLinearVelocity` /
`m_deltaVelocities`). Regression test: `rb_mb_contact_impulse_not_doubled`
(equal-mass head-on converges to the shared inelastic velocity).

### Implementation problem found and fixed

**Mirrored feedback force in the contact writeback.** The per-link/base
constraint-force accumulation copied Bullet's
`writeBackSolverBodyToMultiBody` formula (`force = m_contactNormal2 · λ/dt`)
verbatim, but Bullet's manifold normal points B→A while ours points A→B — the
accumulated wrench was sign-flipped, so the constraint-pass reaction opposed
Bullet's (impact spikes +700 vs −824; the frictionless rest settled at

was unaffected — only the reported force was wrong. Fixed by accumulating the
*physical* contact force per side (A along `−normal`, B along `+normal`,
matching torque flips) in `writeback_contact_rows`; after the fix the resting
reaction converges to exact statics like Bullet's.

### Bullet's gravity blind spot on mb↔rb constraint rows (not ported)

Measured with an instrumented probe (a welded ball given a 3 m/s +Y velocity:
the row impulse comes out at exactly +3.000000): Bullet's
`fillMultiBodyConstraint` reads `rb->getLinearVelocity()` for the row's
relative velocity — which at assembly time **does not include the current
gravity step**, because Bullet keeps rigid-body gravity as an accumulated
force and injects it as `m_externalForceImpulse` only at the writeback
(`setLinearVelocity(snapshot + externalForceImpulse)`). Its rigid-rigid joint
rows add the same impulse at assembly (`convertJoints`), but the
multibody-vs-rigidbody path does not. Consequences on Bullet's side: the rows
cancel the pre-gravity velocity (a 3 m/s initial velocity disappears without
a trace), then the writeback injects one gravity step (vy = −g·dt) which the
next frame's rows recover only ~20% of — a geometric vy decay of ×0.8 per
frame and a finite sag of g·dt²·Σ0.8ⁿ ≈ 1.36 cm. Our rows see the
gravity-integrated real velocity (our engine integrates gravity into the
velocities before the solve, the recorded rigid-solver deviation), so the
locked rows cancel the full gravity step each frame and hold the weld exactly
— physically the stiffer and correct behavior, kept as a deviation.

## Inverse-dynamics probes (2026-10-22, M1/M2)

Bit-level `cmp` comparison (not mbdiff tolerance) against the stock
`BulletInverseDynamics` library: `tools/inverse_dynamics_probe.cpp` plus the
Rust twin `crates/bullet-physics/examples/id_probe.rs` (which exercises the
facade's optional `inverse-dynamics` re-export), built by
`tools/build_inverse_dynamics_probe.py` against the IEEE-precise BID in
`target/bullet3-build-id[-double]` — the main-rig `/fp:fast` default swaps in
approximate trig that diverges 1 ulp from ucrt and would drown the comparison
(design doc `docs/design/inverse-dynamics.md` §4). Protocol: 7 scenes × 3
states × 4 groups, every scalar printed at C `%.17g` — `S1` inverse dynamics
(generalized forces + world getters, gravity folded into the accelerations),
`S2` gravity-free kinematics, `M` the joint-space mass matrix (n², row
major), `J` the world-frame jacobians (per body dot(J_T)u, dot(J_R)u, jac_T,
jac_R). Scenes 0–3 are canonical trees (revolute arm / mixed chain / floating
base / spherical arm); scenes 4–6 are seeded random trees — `srand(seed)` vs
`CrtRand::seeded` replicating the MSVC sequence under a shared draw protocol
(upstream's generator `Extras/IDRandomUtil` sits in the zlib-excluded zone,
so the probe carries its own).

The rig caught three port-side deviations during M2, all fixed and pinned in
code comments: `btVector3 operator/(vec, scalar)` is `v * (1.0/s)`, not true
division (`btVector3.h:843-856`) — three call sites; the CRBA subtree
centroid accumulates the child terms first (`a += (b + c)`); joint-axis
normalization squares via `btPow(x, 2)` (`MultiBodyTree.cpp:269-271`),
guarded against LLVM strength reduction with `black_box`.

| Precision | Result |
|---|---|
| f64 | **84/84 group lines byte-identical** (7 scenes × 3 states × 4 groups; 0 diff after CRLF strip) |
| f32 | Scenes 0–5 fully identical. Scene 6 (5 bodies / 19 dofs — revolute root, two floating links, a spherical branch) residual: **45 of 10083 emitted tokens** — `M` differs in all 3 states (coupling entries of dof 14, the branched spherical joint's middle axis, against body 1's floating translation dofs and the body-0 revolute dof, plus mirrors), `S1`/`S2` one state each at a single tau slot; `J` clean and all `S2` kinematic slots clean |

Classification: **floating-point rounding-order noise, accepted** — the f64
bit-exactness pins the operation sequence as semantically identical, and the
f32 residual is deterministic, exactly 1 ulp per differing entry, and
confined to one branched-tree scene. The earlier dense-axis suspicion is
refuted by scenes 4–5: they exercise the dense-axis normalization and
revolute axis-angle paths and are bit-exact, so the residual is specific to
scene 6's coupling arithmetic, not to any axis-handling path. `S2`'s single
diff token is the tau echo of the `S1` row (both probes reprint the last
computed generalized forces), not a kinematic value. Per the project bar —
aligned-or-better simulation, parity as the floor rather than the goal — the
residual is recorded here instead of being chased to bit equality.
